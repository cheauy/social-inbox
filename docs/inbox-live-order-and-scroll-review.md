# Inbox live ordering, membership and scroll correction

Confirmed causes: the shared `stableConversationOrder` policy deliberately kept old row positions and appended new rows; a temporary discovery marker was retired once a server response included a row, allowing a later stale/filtered response to omit it. Paged view replacements also cleared targeted pending IDs without qualifying them for the new view. A slow page response could publish its stale row version back to shared state.

Latest message activity now orders rows within the existing pinned/unpinned groups; equal activity keeps tie positions. Incoming/teammate previews cannot regress to an older message timestamp. Filtered server props retain already hydrated, authorized rows, and the existing client predicates continue to enforce All, Unread, Comments, Pinned, status/channel and Smart Views. Stale props preserve the whole newer local row. Revoked workspaces and rows outside the active channel/workspace scope are excluded.

Paged replacements qualify visited/pending IDs on the server in batches of at most 200. A slow response uses a newer live version when available, and rows changed during the request are queued for a bounded follow-up qualification rather than removed by the older result. Existing generation/abort checks prevent an earlier view/search response from replacing the current view. No frequent whole-inbox polling or migration was added. The production legacy fallback remains supported; live paging RPCs were reported absent by the parent read-only audit, so the paged path is verified locally rather than claimed active in production.

The list now captures the visible conversation and offset on scroll and restores that anchor after activity reordering. Native anchoring is disabled for this list to avoid double adjustments; deferred row height changes use the existing manual height anchoring. This does not scroll to an updated/selected row or force the list to its top. If the anchor is filtered/removed or no longer rendered, the existing numeric viewport is left alone; exact anchoring is therefore not guaranteed across removal, filter changes or window boundaries.

Explicit conversation opening still scrolls its message pane to newest. Subsequent incoming/teammate updates while reading history now preserve that position and use the existing Latest/new-message indicator. Duplicate delivery updates do not jump the pane. List and message scroll refs remain independent.

A suspended browser cannot execute continuously; existing bounded catch-up runs after foreground/reconnect. No real customer messages, push, deployment, production SQL or database writes occurred. Earlier review notes describing fixed list positions are superseded by this user-requested latest-activity ordering.

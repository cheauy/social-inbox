# Payment checkout cancellation

Local work only. No hosted migration, provider call, financial transfer, refund, configuration change or deployment has been performed. `PAYMENT_CANCELLATION_ENABLED` remains **false**. The production compatibility gate and status readers continue to use the installed schema.

The user rejected the proposed per-user/workspace QR creation limits. They are withdrawn and are not implemented. No equivalent QR count or waiting-period cap replaces them. QR generation is local; a bank inquiry is a separate operation with a limited provider budget.

## Completed popup behavior

The QR card appears in a centered responsive native dialog with internal scrolling on short screens. The original server countdown is at top right beside a separate 44px X. Receiver, exact amount/currency, QR bytes and quiet zone stay unchanged. Outer workspace/plan/term/reference text is inside collapsed Payment details. Waiting has a decorative spinner and `aria-busy=false`; Checking payment requires a real verification request. Error, review, expired and completed states stop animation; reduced motion is respected.

X/Escape dismisses to `/dashboard/subscription`, restores connected opener focus, and does not cancel a payment, switch workspace, extend expiry, create a QR or change a plan. Saved status and mutation identity retain the immutable business ID. The nested confirmation releases focus before its result can dismiss the checkout.

Future Cancel payment is an explicit confirmed server POST. Only saved `checkout_closed`/`expired` results navigate away. Failure/uncertainty stays visible. A closed purchase intent is never resumed; a later explicit plan selection uses a fresh identity/reference/QR if the server says it can be issued. Closing a checkout never revokes a saved bank QR or proves no transfer occurred. Closed unpaid saved-status views do not start automatic inquiries; an explicit reconciliation request remains possible subject to authoritative capacity and lifetime limits.

## Revised accounting candidate: no QR creation cap

The previous lifecycle draft held unused reservations until expiry plus one hour. A real isolated SQL reproducer demonstrated 30 create/close cycles by one owner reserving all 90 slots while making zero provider inquiries. The correction is accounting, not an additional customer issuance limit.

Candidate: `db/proposals/20261016105717_bakong_closed_checkout_accounting.sql`. The filename was generated with the existing Supabase CLI `migration new`; this file is deliberately **outside the active migration queue**. It is tested only against isolated fixtures containing the older cancellation/lifecycle drafts. It is not a complete production bundle and must not be applied alone.

The candidate reserves unused future checks only for unclosed, unexpired pending/review attempts without a confirmed hash. Customer closure or original expiry releases those unused promises immediately. It never removes or refunds a `provider_calls` row. Every claimed inquiry, including in-flight, failed, timed-out or lost-response claims, remains counted conservatively against rolling 24-hour usage and the attempt's lifetime count.

Preparation, claim and KHQR cancellation use the same environment budget lock before the subscription/attempt write locks. Cancellation keeps the existing lease ID, lease deadline, cooldown, check count and claim evidence. A provider response arriving after closure can finish its original claim and persist evidence exactly once. The old lifetime cap of three and five-minute check spacing stay intact. No per-user/workspace QR quota, actor lock, issuance counter, arbitrary waiting period or new provider allowance is introduced.

The existing global invariant remains: rolling-24h claimed usage + reservations for other open attempts + the requested inquiry must fit the approved budget, capped at 90. A fresh checkout still needs capacity for its three promised checks. Cancellation releases unused promises; it cannot release usage already claimed. The installed per-environment budget scope and provider authorization checks are preserved.

Critical reservation/blocking/conflict helpers intentionally use `VOLATILE` read semantics so revalidation after locks sees a fresh snapshot, rather than inheriting a calling-query snapshot. The atomic proposal checks this property, and a regression test changes the baseline in a calling SQL statement before checking conflict. This follows [PostgreSQL17 function snapshot rules](https://www.postgresql.org/docs/17/xfunc-volatility.html); it does not substitute for independent-session barrier tests.

| Operation | Already claimed usage | Unused reservations |
| --- | --- | --- |
| Create one open QR | 0 | 3 |
| Claim its first inquiry | 1 | 2 |
| Cancel it with that claim in flight | 1, retained | 0 |
| Explicitly create a new QR | 1, retained | 3 for the new QR |
| Request an old closed QR inquiry | Increases only if global spare capacity and its lifetime cap allow it | Does not take another open QR's reservations |

This permits ordinary Cancel -> new QR cycles without accumulating reservations for every closed checkout. It does **not** mean unlimited bank calls or unlimited simultaneously open payable checkouts. If the 90-query budget is genuinely consumed, a fresh payable QR must wait for capacity. If it is fully reserved by still-open checkouts, their promises cannot be spent on old closed QRs.

Unlimited closed QRs and a fixed provider budget cannot also guarantee three future late-payment inquiries for each old QR. The candidate makes those inquiries best effort from spare capacity, with at most three lifetime checks per old attempt. Saved records, QR identity, original deadline, cancellations, claimed calls and confirmed evidence are retained even when no check is available. No automatic polling of closed views spends the newly released capacity. Support review is the practical fallback when a late transfer cannot be confirmed within the budget; never label that uncertainty unpaid or ask a customer with confirmed funds to pay again.

## Late confirmed funds: review without financial actions

The local candidate preserves cancellation/expiry review guards. If late funds are confirmed while a replacement KHQR is pending or verified-but-not-applied, it puts that replacement in review and hides its payable display under the same transaction. Further money received through a saved QR is also preserved in review. The guard prevents automatic replacement application while related confirmed funds await review. If the replacement already applied first, its paid plan and invoice stay unchanged. Closing/holding a checkout is not bank revocation, refund or plan cancellation.

The existing admin Reconcile helper returned known `verified_hash` review rows unchanged. The local admin route now returns HTTP 409 `SETTLEMENT_REVIEW_REQUIRED` with an explicit operator-resolution requirement instead of presenting that no-op as success. It does not issue another bank inquiry or change money/entitlements.

The user selected **explicit admin approval of the original plan after verified receipt, only without an overlapping/replacement purchase or changed subscription baseline**. This is now implemented locally in `20261016111428_bakong_admin_original_plan_resolution.sql`, the admin route, and `BakongOriginalPlanButton`. It uses the canonical freshly verified TENH administrator identity; the browser cannot select an actor, business, plan, price or currency. The server requires explicit confirmation, a 10–500 character reason, the reviewed immutable transaction reference and an idempotency UUID. The database rechecks authoritative matching settlement/purchase evidence, active purchaser billing access, original baseline and cross-provider replacement conflicts under the budget/subscription/attempt locks. Later closed replacement QRs are conflicts too because they may still receive money. Earlier closed unpaid attempts alone do not impose a new QR creation limit.

Successful application uses the existing financial algorithm for the immutable original purchase, produces exactly one invoice, and atomically appends a private immutable actor/reason/evidence/decision audit. Activation failure rolls back the plan and invoice together while preserving receipt evidence and the failed decision. Mandatory audit failure rolls back the entire application. Lost acknowledgements retry the same request identity; they never repeat the entitlement or inquiry. Confirmed conflicts stay in review with machine reasons and clear admin messages. No automatic late activation, refund or transfer exists. The control and writer paths remain gated off for production. Enabled KHQR preparation, cancellation and admin resolution additionally require the full schema capability marker, so an older/partial schema cannot accept their writes.

History/status must distinguish checkout Closed/Expired from settlement Unknown/Confirmed-needs-review. Keep saved status and support references reachable. A resolved review must not reset usage, lifetime checks, original expiry, or unrelated provider obligations.

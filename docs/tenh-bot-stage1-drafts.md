# Tenh Bot Stage 1 — local drafts only

Subsequent local completion: tenh-bot-stage2-drafts.md documents all seven selected Stage 2 draft-only types and their NEW tests; queued/unimplemented descriptions below are historical to this earlier batch.
Implemented: a shared tenant/channel-scoped rule contract, bounded pure evaluator, five draft editors and synthetic conversation tester on the existing top-level Tenh Bot page. The existing comment-rule UI, permission guard and API are reused. No Settings navigation, database migration, worker wiring, credential or scheduler change is added.

The five kinds are Welcome/Away, Keyword FAQ, Autoassign/Human Takeover, Unanswered Staff Alert and Conversation Menu. Templates are configurable per draft; no owner's business answers are shared between tenants. Drafts exist only in the mounted editor session; changing channel, clearing drafts or leaving the page removes them. The server page keys the editor by business so a workspace change resets session drafts.

## Behavior and boundaries

- Welcome applies to an explicitly simulated first contact during configured business hours; Away applies outside those hours. The evaluator supports individual weekdays, overnight hours and IANA timezone/DST conversion. The initial UI configures Monday–Friday, one interval per day; richer schedules can extend the existing contract.
- FAQ uses literal, Unicode-normalized, case-insensitive keyword containment. No regex or language model is executed. Higher priority wins, then stable rule ID. At most one customer reply is proposed per event. A per-recipient/per-rule cooldown spans sample conversations.
- Assignment proposes only active existing workspace staff permitted to the tester. The initial UI selects one staff member, not load balancing. Pure tests preserve an existing sample assignment; the UI/API does not inspect or change real conversation assignments. Human keywords or a staff reply hold customer responses until an explicit synthetic staff resume. Bot echoes do not trigger rules.
- Unanswered alerts are prospective internal staff proposals with due times. A later customer event replaces the prior deadline; a staff answer cancels it. They are not delivered, persisted or scheduled. Only staff from the authenticated workspace are selectable; there is no external destination.
- Menu commands preview configurable text choices and exact-label responses. Provider quick-reply buttons are not implemented or represented as available.
- Synthetic events are sorted deterministically and deduplicated by authenticated business, connected channel and event ID. Maximum 20 rules/100 events, bounded strings/menus/staff lists and 256-KiB draft payload validation. A direct-customer hypothetical 24-hour window is required for proposed responses; human-agent and comment reply extensions are never used. This is planning logic, not proof of provider eligibility.

Live execution is structurally unavailable: mode must be `draft`; the module imports no database/provider/worker/timer; API output sets `dryRun=true` and `executionAvailable=false`. `/api/facebook/auto-reply?scope=drafts` reads connected-channel and permitted staff metadata; POST operation `draftPreview` authenticates channel management, rechecks tenant-owned active Facebook channel and staff permissions, validates rules, and returns a plan. No write/queue/provider call occurs. Other channel previews return unavailable. The existing comment worker/recipient reservations remain untouched.

Meta's official Messenger send and quick-reply documentation returned HTTP 429 during this stage's verification. No supported live trigger/send contract was established for these new drafts. Automated provider sends, actual human-takeover transactions, recipient reservations and durable idempotent/cancellable jobs must be separately implemented and tested before activation. The in-memory evaluator is not a race-safe multiworker ledger and is never used as one. Reuse/extend the existing safety ledger rather than creating a second live sending system.

## Effective rules

- Fresh password/OAuth sign-in creates an immutable policy linked to verified user ID and provider `session_id`. The server reads `auth.sessions.created_at`; client clocks, metadata and submitted duration values cannot select or extend expiry.
- Unchecked Remember me: nonpersistent browser-session cookies and an absolute application maximum of 86,400 seconds. Browser restoration can preserve session cookies; closing a browser is not guaranteed logout.
- Checked: current global integer duration, default 30 and range 1–90, snapshotted at successful authentication. Application expiry is authenticated time plus days × 86,400 seconds, capped by an available stricter provider `not_after` value. Later refresh, activity, tabs, workspace changes and policy edits do not extend that snapshot. A later shorter provider cap/revocation/account disablement can still deny access.
- Existing unbound sessions retain their prior persistence during the reviewed compatibility phase. They are not silently enrolled or renewed. Explicit enforcement activation requires a fixed legacy cutoff, finite grace deadline and recorded native rollout approval. After that deadline, unknown old sessions must authenticate again; unknown sessions created after cutoff are denied. Bound expiry/revocation is enforced even during compatibility mode.
- New duration edits affect new logins only. The API requires the configured TENH administrator, verified AAL2 and a fresh MFA method within ten minutes. An atomic immutable audit stores actor, server time, previous and new duration. This UI has no revoke-existing-sessions action and cannot enable rollout enforcement.
- Recovery sessions are excluded from normal pages/data. Reset authorization lasts at most ten minutes after verified recovery and is consumed atomically before writing the password. Concurrent/replayed grants cannot write twice. Known failure requires a new link; an uncertain write revokes application sessions and reports uncertainty rather than promising the password stayed unchanged.
- Successful recovery requires fresh login and attempts global provider/application revocation. A failed remote revocation is reported honestly. Existing password-change behavior retains the current device and supports the explicit other-device revocation choice; both the application ledger and provider scope are used.
- Device logout uses explicit `local`; all-device logout uses explicit `global` with confirmation; the settings page's existing others action uses `others`. Local UI/cookies/private cache/channels are cleared even when remote revocation is uncertain. Session-scoped cross-tab messages cannot clear a newer login.
- Dashboard validation uses server time, hides private content on expiry or validation failure, aborts stale requests, limits retry backoff and stops automatic retries after six failures. Revalidation on visibility/BFCache restore is covered by mocked browser events. A hard reload separates changed user/session identity from old server-rendered content.
- Shared rate limits use atomic PostgreSQL counters and HMAC-derived IP/account keys. Configure a header only when the trusted ingress overwrites it; absent configuration uses a conservative shared IP bucket. Process-local password counters are supplementary, not the security boundary.

## What enforces access

Default server clients validate the policy after verified `getUser`; explicit raw clients are limited to fresh login, typed provider callbacks and logout/recovery flows. New session records can be created only by the service-only binder after successful authentication, not by clients or refresh/init requests.

The migration adds restrictive predicates to existing RLS-enabled public tables, Storage objects and Realtime authorization messages without granting tenant access. A reviewed PostgREST pre-request hook is additionally required to cover views, non-RLS tables and SECURITY DEFINER RPCs. Existing hooks must be inspected and chained, never blindly overwritten. Service-role jobs/integration webhooks remain separate from human-session authorization.

Browser-readable signed hints carry persistence/display identity only. The browser decodes them for cookie attributes and cross-tab disambiguation; it does not verify their MAC. The server verifies the MAC, and the private database ledger remains the authorization authority. Editing a hint cannot extend application access.

## Remaining external boundaries — not production-ready

1. Hosted Auth settings were not queried and remain **unverified**, including email confirmation, password strength/leaked-password checks, OTP length/link expiry, JWT duration, refresh reuse interval, inactivity/timebox/single-session rules, secure password change, email templates, SMTP, redirects and MFA enrollment/recovery. Current docs describe capabilities; they do not prove project configuration.
2. Direct Supabase Auth `/user` password writes are outside application RLS and PostgREST hooks. The provider's secure password-change/recent-auth configuration must be reviewed before claiming the Next.js proof checks cover that endpoint. No provider setting was changed here.
3. Existing private Realtime Presence/Broadcast authorization is cached at join/new JWT. Client cleanup disconnects cooperative clients, and table changes use RLS, but this is not a guarantee of immediate removal from an already authorized private channel. Review token-expiry/channel revocation strategy before enabling strict rollout.
4. Already issued signed URLs are bearer capabilities. Existing Storage read/download URLs last 300/600 seconds; signed upload URLs have a separate provider-documented two-hour lifetime. This patch does not retrospectively revoke those capabilities or claim cached/downloaded bytes disappear. Review tighter issuance/reconciliation strategy if a hard capability deadline is required.
5. Native password/OAuth login currently talks directly to the provider and does not bind the new application policy. Native login support/reauthentication must be reviewed before enforcement; the draft requires an explicit native plan reference to activate. No native files were changed.
6. Real provider email/callback flows were not executed. The strict web recovery callback requires a recovery-purpose `token_hash`; it deliberately does not accept a browser/URL success flag or assume a bare PKCE `code` proves recovery. A reviewed Recovery email template must point to canonical `/auth/recovery?token_hash={{ .TokenHash }}&type=recovery`. Review signup token-hash links/OTP templates, invitation `next` handling and native compatibility together. Default/unreviewed code-only reset links will fail safely until this configuration is completed.
7. Application baseline password checks are 8–128 characters with a letter and number, matching the existing local rule; actual stronger provider settings remain unverified and must be tested. Provider OTP length/expiry is not hardcoded.
8. Provider sign-out revokes refresh/session credentials according to its supported semantics. Existing access JWTs are not universally invalidated instantly. Ledger/session-existence checks deny covered data paths, subject to hook installation and the Realtime/signed-capability limits above.

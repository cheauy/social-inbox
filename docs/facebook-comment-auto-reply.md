Top navigation is Inbox | Tenh Bot | Analytics. Tenh Bot opens its dedicated /dashboard/tenh-bot page inside the existing dashboard shell, inheriting DashboardHeader without adding a separate sidebar. The three-step web workflow chooses scope, composes separate replies with preview, then reviews before saving. Choose one, several, or all currently authorized connected Pages. All Pages is an explicit snapshot; newly connected Pages require deliberate addition. Choose one/several verified numeric Facebook /posts/ or permalink.php links (or Page_post IDs), or all posts including future posts. There is no equal-specificity priority ambiguity because the unique Page/post scope rejects duplicates. Mobile provides the same scope options and reviews via its existing native controls; no full Expo/device test was available.
Separate public/private plain-text templates are supported. Drafts are disabled. Pause before editing.
Activation requires an explicit start with timezone. Eligibility starts at the later of the requested start and server activation timestamp. Choosing an earlier time today does not backfill old comments.
The read-only test checks an existing inbox comment and fresh Facebook eligibility without creating jobs or sending. It deliberately ignores draft activation/cutoff during eligibility inspection; actual sends enforce both.

## Implementation and cost
20260930_facebook_auto_reply.sql adds rules, one compact job per comment/action, and private-recipient reservations. It does not copy comment bodies, media, or webhook payloads and never scans posts.
Fresh installs do NOT attach the legacy messages INSERT helper. DO NOT deploy the initial schema alone: 20261001_facebook_auto_reply_safety.sql adds background recovery and detaches any older installed trigger, so feature failures cannot reject core inbox inserts. The worker processes at most 100 existing durable incoming comment records per recovery transaction through a new partial (created_at,id) index, then claims at most five actions. No post polling or raw-payload duplication is added. Duplicate comment/action keys cannot enqueue twice. Page-owned comments, echoes, and missing original timestamps do not queue.
Recovery no longer uses a timestamp cursor or finite age lookback. 20261002_facebook_auto_reply_recovery_test_gate.sql adds messages.facebook_auto_reply_processed: existing rows receive the constant metadata default true (no backfill), then the default becomes false for future inserts in the same short DDL transaction. A partial (created_at,id) index contains only unprocessed incoming add-comments. Each repair locks at most 100 pending rows with SKIP LOCKED, enqueues, and marks them processed in one transaction. A comment committed after newer comments were repaired remains indexed/pending regardless of its timestamp or transaction duration. Failure rolls back markers and jobs together and stops the worker observably before sending. Missing/invalid pending indexes fail closed; the function checks index shape and discourages sequential plans. The old cursor is retained only for compatibility/audit, never consulted by current recovery.
This removes the known commit-order loss mechanism, assuming committed message records remain present, inbound writers use the default marker, and supported schema/index/grants are installed. No trigger or inbox INSERT feature SQL is added. Intentional pause/cutoff/ineligible-comment skips remain policy decisions, not promised sends. SQL faults leave pending work visible and retryable rather than silently consumed; the worker returns HTTP 503 on repair failure and reports repaired count on success. This adds one boolean/index entry and a bounded background marker UPDATE per new comment, with ordinary row-update/Realtime/VACUUM costs; it does not remove database load. Real multi-connection contention, live locks and concurrent index build still need verification on an isolated PostgreSQL instance before deployment.
Specific-post scope wins over all-post scope; unique Page/scope prevents ambiguous duplicate rules.
Webhook background work is scheduled with Next 16 after() only for comment additions and only if the worker flag is enabled. The response does not wait for outbound sends. Ordinary inbox reads and DM handling do not call this worker.
Each batch claims up to five jobs with FOR UPDATE SKIP LOCKED. The public action completes before private for that comment. Separate durable statuses preserve partial outcomes.
The send boundary rechecks rule activation/pause and Page connection, then reserves private recipients atomically. Concurrent private replies to the same Page/customer are suppressed. A confirmed subsequent customer DM permits a later reservation.
Fresh Graph comment identity, original creation time, public replies, private eligibility, and the existing Messenger reply policy are checked before POST. The automation sends private messages only with recipient.comment_id; it never uses HUMAN_AGENT or starts ordinary inbox auto replies.
Unknown reply pagination/state fails closed. Both-mode ignores only its own confirmed public sibling before private sending.
Read/write retries are bounded to four claimed attempts with exponential backoff. Definitive Meta throttling/auth rejections can retry. Transport failures, malformed acknowledgements, code 1, and server/transient send errors never blindly resend.
Expired preflight leases can recover; expired sending leases become needs_review. Public uncertainty gets bounded read-back reconciliation, including one recovery attempt after a crashed worker. Private uncertainty requires checking Facebook because the original recipient identity is not sufficient to safely infer a Messenger thread.
Only an uncertain/in-progress send temporarily retains its reply text for reconciliation; confirmed sends clear that snapshot. Outgoing inbox message records remain the authoritative content history.
Both per-rule pause and the visible tenant-wide Pause all are checked before the send boundary. A missing tenant control is paused by default. Paused/old-generation queued work is retired in bounded batches of ten rather than an unbounded update during a customer request. Global resume uses a fresh cutoff and does not release old queued work. Five consecutive failed/retry/uncertain outcomes open a 15-minute tenant safety cooldown; claimed jobs recheck it before sending. At most ten expired leases are recovered per batch. Sends already across the durable boundary may finish. Remote manual sends can race an external API read; no local lock can prevent a Facebook/Business Suite operator from replying between that read and POST.

## Setup requiring separate approval
1. Confirm the exact target, a usable backup/recovery point, existing schema and grants. Keep the worker off. Apply the original migration ONLY if absent, then both reviewed safety/recovery-test-gate migrations before enabling workers. Do not blindly reapply the initial schema. Validate UUID keys, processed-marker defaults, pending index validity/predicate, function ownership, service_role grants, and real multi-connection behavior first.
2. Deploy the reviewed code after approval.
3. Confirm Page permissions/Meta eligibility for public comment management and private replies. Public post verification and private replies fail closed if Meta refuses access.
4. Use the existing CRON_SECRET. After approval, configure a queue-only recovery schedule for GET /api/cron/facebook-auto-reply (for example once per minute), authorized with Bearer CRON_SECRET. vercel.json has deliberately not been changed.
5. After approval, set FACEBOOK_AUTO_REPLY_WORKER_ENABLED=true. Until then cron returns paused and webhooks never start sends.
6. Agree the customer's exact start/cutoff timezone, save/test a draft, then explicitly turn it on. A real public/private send test needs user approval.

Rollback: set FACEBOOK_AUTO_REPLY_WORKER_ENABLED=false, global-pause and pause rules, then reconcile/drain sending/needs_review before rolling back code. Keep jobs, reservations, controls, processed markers/pending index, test budgets and obsolete recovery cursor for audit/idempotency. Never restore the unsafe synchronous trigger OR cursor-based recovery as automatic rollback. If an old trigger is still attached and ingestion is affected, the first separately approved emergency schema action is detaching that exact trigger; retain tables/functions until dependency review. Do not drop tables or delete data as rollback.

Migration risk: the original file is not rerunnable. The follow-up is rerun-tested against the expected schema only; IF NOT EXISTS does not verify an arbitrary remote table/index shape. The recovery index uses CREATE INDEX CONCURRENTLY outside the function transaction; cancellation can leave an invalid index that requires a reviewed repair. Two-second lock timeout and 60-second statement timeout bound attempts, not guarantee zero impact. Trigger detach/DDL still needs a brief lock. The function transaction rolls back on failure, but the concurrent index is a separately committed artifact. Whole-database recovery can lose legitimate inbox writes after the restore point and cause downtime; it is not an ordinary feature rollback.

## Disabled-by-default bounded live-test gate
The new facebook_auto_reply_test_gates table is operator-only (no customer API/UI can configure it). Inserts are forced disabled and counters zero. A later separately approved arm operation requires an exact tenant, connected Page UUID AND platform Page ID, numeric Page_post ID, exact comment ID, explicit public/private caps (0 or 1 each), and expiry within 15 minutes. Armed identity, caps and expiry become immutable. Budget counters only increase and survive failed/uncertain sends or process crashes; service_role cannot delete the gate. The existing comment/action dedupe remains in force.
Only one gate can be active deployment-wide. While armed, claim processing holds non-target and other-tenant jobs without sending or discarding them. The atomic begin_send gate independently rechecks exact Page/post/comment and reserves the action attempt before POST, under row locks. A confirmed rejection, timeout, or crash NEVER refunds the budget; a private uncertainty remains needs_review. Caps therefore bound POST attempts, not just successful deliveries. Zero-cap/exhausted targeted actions receive a clear skipped reason. An enabled expired/exhausted gate stays restrictive and never silently returns to normal sending. Global pause is required to disarm; disarming removes the test restrictions and must be separately deliberate.
Safe eventual test sequence after all setup approvals: worker off and in-flight sends drained/reconciled; tenant paused; save the approved exact-target rule disabled; configure the exact test gate disabled; obtain explicit arm/cutoff/action-budget approval; arm gate and activate only that rule; resume tenant and approved worker/scheduler; observe at most the allowed public/private attempts; stop worker/global pause before any gate disarm. This affects Auto Reply queues only, not normal inbox ingestion. No gate was configured or armed remotely in this work. Fixtures alone simulate arming and budget consumption.
